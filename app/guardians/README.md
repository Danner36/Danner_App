# guardians

Cleveland Guardians dashboard, authorized playback list, and isolated players.

Playback URLs are not stored here. Phones fetch root `guardians_streams.json` from GitHub `main`.

## Behavior

- Loads the Guardians season record, today's or an active game, score, and only remaining games from MLB, with a ten-minute schedule refresh and pull-to-refresh. The season record sits as compact win–loss text under the Guardians title. A live featured game also refreshes its park-style scoreboard every five seconds while the screen is open.
- During a live game, the featured card shows a park-style scoreboard with inning-by-inning runs, runs/hits/errors, balls, strikes, outs, and the current batter and pitcher numbers. That board is hidden before first pitch and after the game is no longer live. Icon-only Play controls sit under the featured card.
- After today's game is Final, the same featured card becomes the recap through local midnight of that official date: a `WIN`, `LOSS`, or `TIE` badge, `Home vs` / `Away v`, `Final` or `Final/10`, and the Guardians-first score. Play, Listen, Get video, the countdown, the park-style scoreboard, and pitcher names stay hidden. A later game still today keeps the featured card; a doubleheader recap is the last completed game of that official date.
- Promotes a live game, today's next game, or today's Final recap above the schedule, counts down every second before first pitch, states delays directly, and enables approved icon-only Play controls 15 minutes before game time. The today card badge includes the local start time and names the game `Home vs` or `Away v` the opponent. The upcoming schedule still uses `vs` and `at`.
- Fetches approved playback URLs from root `guardians_streams.json` on GitHub on screen open and every minute, with the last valid file cached on the phone. Entries match normal dates and MLB game numbers; one URL can cover multiple dates.
- When the featured game is inside the 15-minute video window and no valid matching URL is in that file, the card shows **Get video**. That button calls the Cloudflare Worker, which starts the GitHub Actions extract pipeline. While it runs, the card says **Getting video. This could take a minute.** and checks the worker `GET /streams` list every five seconds without using the phone’s last saved file, until a valid stream appears, then shows Play. Get video stays hidden in the local test harness unless that launch sets the worker URL and family PIN.
- Keeps completed games out of the schedule and formats start times in the phone's time zone.
- Uses HTTPS by default; cleartext HTTP requires `allowInsecureHttp: true` on that entry. Direct media uses the native player. A matching `direct` source also exposes an icon-only Listen control that plays the same URL with no visible video, a stop control while audio is playing, and lock-screen now-playing controls. Returning to the hub stops the audio. On iPhone, that player's system controls include AirPlay. On Android and iPhone, a header Cast control appears only for `direct` sources and loads the JSON URL on the default Cast receiver. Isolated `web` sources show a header TV control. When the approved page reports a castable HLS, DASH, or MP4 URL, the phone relays that stream from a LAN origin and Casts the relay, because the provider answers its playlists only for its own page and its segments carry no CORS header the receiver needs. If the page never reports one, the control says so; the screen-capture converter is archived under `reference/screen-capture-hls/` and is not built. Closing the player stops the relay. YouTube and other approved pages use isolated WebViews that promote approved popup targets and discard all others. On iPhone, isolated `web` pages report an Android Chrome user agent so the page serves the same player build as Android. YouTube sources do not offer Listen or TV send.
- Android hardware Back closes the Play modal first, then returns to the hub. Send to TV asks for notification permission for its ongoing relay notification, and shows a failure when no relay can start. On Android the relay runs in a `dataSync` foreground service holding a wake lock and a Wi-Fi lock, so the TV keeps playing after the screen goes off.
- Isolated `web` entries load the exact page URL from the JSON file. The app does not detect or require a specific website or player library. On iPhone, HTML5 `video` and `audio` tags on that page are opted into system AirPlay, and the WebView reports an Android browser so a page that branches on the user agent serves its non-iPhone player. That branch is what keeps iPhone playback on native HLS: a Media Source Extensions player cannot be sent to AirPlay, so removing the user-agent override also removes iPhone AirPlay. YouTube embeds are not injected and keep the system user agent. The player holds the screen awake while it is open, since an embedded WebView leaves display power to the host app. The phone remains the origin while a web source is sent to a TV.
