# guardians

Cleveland Guardians dashboard, authorized playback list, and isolated players.

Playback URLs are not stored here. Phones fetch root `guardians_streams.json` from GitHub `main`.

## Behavior

- Loads the Guardians season record, today's or an active game, score, and only remaining games from MLB, with a ten-minute schedule refresh and pull-to-refresh. The season record sits as compact win–loss text under the Guardians title. A live featured game, or one past its start time that MLB has not yet marked live, is polled every five seconds through `schedule?gamePk=…&hydrate=linescore` while the screen is open and the app is in front. That poll updates the board, score, and game state; Final, and the countdown reaching first pitch, refresh the schedule at once. Warmup counts as pre-game. A poll still in flight skips the next tick, and an older response never replaces a newer one.
- During a live game, the featured card shows a park-style scoreboard with inning-by-inning runs, runs/hits/errors, balls, strikes, outs, and the current batter and pitcher numbers. That board is hidden before first pitch and after the game is no longer live. Icon-only Play controls sit under the featured card.
- After today's game is Final, the same featured card becomes the recap through local midnight of that official date: a `WIN`, `LOSS`, or `TIE` badge, `Home vs` / `Away v`, `Final` or `Final/10`, and the Guardians-first score. Play, Listen, Get video, the countdown, the park-style scoreboard, and pitcher names stay hidden. A later game still today keeps the featured card; a doubleheader recap is the last completed game of that official date.
- Promotes a live game, today's next game, or today's Final recap above the schedule, counts down every second before first pitch, states delays directly, and enables approved icon-only Play controls 15 minutes before game time. A delayed game that has not started keeps a 30-second clock so that window still opens. A game MLB marks `startTimeTBD` shows `Time TBA` in the schedule and on today's card, and does not count down or open Play until it is live; its date and today check use the MLB official date. A postponed game's makeup stays in the schedule, a suspended game MLB still reports as live does not take the featured card, and a delayed start keeps its card past local midnight. The 60-second refresh and the countdown pause while the app is in the background. The today card badge includes the local start time and names the game `Home vs` or `Away v` the opponent. The upcoming schedule still uses `vs` and `at`.
- Fetches approved playback URLs from root `guardians_streams.json` on GitHub on screen open and every minute, with the last valid file cached on the phone. Entries match normal dates and MLB game numbers; one URL can cover multiple dates. The parser skips the guide strings and keeps the newest 200 entries. A failed MLB request does not hold back a newly published URL, and the error card shows a plain message.
- When the featured game is inside the 15-minute video window and no valid matching URL is in that file, the card shows **Get video**. That button calls the Cloudflare Worker, which starts the GitHub Actions extract pipeline. While it runs, the card says **Getting video. This could take a minute.** and checks the worker `GET /streams` list every five seconds without using the phone’s last saved file, until a valid stream appears, then shows Play. The latest-commit lookup on GitHub runs only after the worker list fails, once per Get video. Leaving the screen, a new press, or a different featured game stops the poll; a rate-limited start keeps polling. Get video stays hidden in the local test harness unless that launch sets the worker URL and family PIN.
- Keeps completed games out of the schedule and formats known start times in the phone's time zone. MLB's unset postseason clock (`07:33Z`, 3:33 AM Eastern) is not shown.
- Uses HTTPS by default; cleartext HTTP requires `allowInsecureHttp: true` on that entry. Direct media uses the native player. A matching `direct` source also exposes an icon-only Listen control that plays the same URL with no visible video, a stop control whenever audio is playing, and lock-screen now-playing controls. Audio stops when the game goes Final, is blocked, or the featured game changes, and starting video stops it. Returning to the hub stops the audio. On iPhone, that player's system controls include AirPlay. On Android and iPhone, a header Cast control appears only for `direct` sources and loads the JSON URL on the default Cast receiver. Isolated `web` sources show a header TV control. When the approved page reports a castable HLS, DASH, or MP4 URL, the phone relays that stream from a LAN origin and Casts the relay, because the provider answers its playlists only for its own page and its segments carry no CORS header the receiver needs. Each player page gets its own message nonce, so only the app's injection can report media. The relay is loaded as a live stream when the source is live, forwards the highest video variant at or under 3.5 Mbps when one exists (otherwise the lowest video variant), and prefetches the live-edge segments. If the page never reports one, the control says so; the screen-capture converter is archived under `reference/screen-capture-hls/` and is not built. While the Cast receiver has that relay, the page pauses and stops its own media load. The page resumes when the receiver goes idle or the load fails. A later TV press opens the Cast dialog again, including while a receiver is already connected, so the session can be stopped or the volume changed; it restarts the relay first if the relay stopped, and reloads the TV after a receiver error. A receiver playback error is shown under the header. Returning to the app restarts a relay that stopped while the phone was locked. Ending the Cast session or closing the player stops the relay. YouTube and other approved pages use isolated WebViews that promote approved popup targets and discard all others. On iPhone, isolated `web` pages report an Android Chrome user agent so the page serves the same player build as Android. YouTube sources do not offer Listen or TV send.
- Android hardware Back closes the Play modal first, then returns to the hub. Send to TV asks for notification permission for its ongoing relay notification, and shows a failure when no relay can start. On Android the relay runs in a `connectedDevice` foreground service with a Stop action, holding a wake lock and a Wi-Fi lock, so the TV keeps playing after the screen goes off.
- Isolated `web` entries load the exact page URL from the JSON file. The app does not detect or require a specific website or player library. On iPhone, HTML5 `video` and `audio` tags on that page are opted into system AirPlay, and the WebView reports an Android browser so a page that branches on the user agent serves its non-iPhone player. That branch is what keeps iPhone playback on native HLS: a Media Source Extensions player cannot be sent to AirPlay, so removing the user-agent override also removes iPhone AirPlay. YouTube embeds are not injected and keep the system user agent. The player holds the screen awake only while it is open, since an embedded WebView leaves display power to the host app. On Android the player WebView does not use incognito, which would clear every WebView's cookies and sign TV Location out of Google; cache and third-party cookies stay off. A page that loads an unapproved URL anyway is stopped and the approved page reloads. The phone remains the origin while a web source is sent to a TV.
